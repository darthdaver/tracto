## Problem

The 2 last corpus oracles losing a step after Step 42 (steve, `OcppVersionTest`): `protocol.` ▸ `getTransport`,
`getVersion` (counted as "nested-block variable" by `missing_tokens.py`: the variable is declared in a `for` loop, but
it is not the cause). `OcppProtocol` is an enum annotated `@Getter`: its getters are generated by Lombok at compile
time and do not exist in the sources, the only thing the symbol solver reads. Lombok is common in Maven projects (in
steve, 209 of 324 main files: `@Getter` 115, `@RequiredArgsConstructor` 94, `@Slf4j` 68, `@Setter` 68, `@Builder` 27,
`@Data` 17, ...; 7 test helper classes): every generated member (getter, setter, builder, constructor, logger) is a
target the model cannot be offered, at generation and at inference.

## Fix

**The members come from Lombok itself (deterministic).** The resolver of the dependencies (Step 38) knows the Lombok
jar of the project (its version): when the project depends on `org.projectlombok:lombok`, for each source root
(`src/main/java`, `src/test/java` of each module), the files that use Lombok (`lombok.` in their text; not the test
classes generated by the pipeline, `…STARSplitTest`) are delomboked by that jar (`java -jar lombok.jar delombok`, no
classpath: 14–20 s for steve) into `processed_libs/delombok/<root, / → __>/`, listed in
`processed_libs/delombok/roots.json`. The date in the header of delombok is removed (the same copies at each run).

**The copies keep the code of the developer.** Delombok reprints the whole file and rewrites code that has nothing to
do with the generated members (seen on steve in a first version: the initializer of a `@Builder.Default` field
removed, a comment moved by the printer; elsewhere `val`, the bodies of `@SneakyThrows`, the null checks of
`@NonNull`). The class descriptions of the contextual information are built from the files the solver reads, so they
showed that rewritten code. `LombokMembers` (`java -jar tracto.jar lombok-members <root> <copies>`, run by the
resolver after delombok) writes each copy as the **original file, byte for byte, with the members delombok marks
`@lombok.Generated` inserted as text before the closing brace of their type** (with their Javadoc: delombok copies the
Javadoc of a field to its getter); a generated nested class (a builder) is inserted whole; an enum without members gets
the semicolon after its constants. A file that cannot be merged (a file that does not parse, a type without its
original) keeps the output of delombok (none on steve: 216 of 216 merged).

**The module.** `DelombokCopies` reads the manifest when the parser of the repository is set; the copies are given to
the symbol solver **before** the sources of the project (the first solver that finds a class wins), so a class
annotated with Lombok resolves to its copy, with the generated members (the members after a value, the types of the
chains). The members after the name of a class (static members, constructors after `new`, member types) are read from
the file of the class (`classPathIdentifiers`): that branch reads the copy (`DelombokCopies.copyOf`). Nowhere else:
the files the pipeline reads as text (the test classes, the model input) are the sources, unchanged.

At inference the resolver runs as at generation (Step 38), so the copies are the same.

Not covered: the features of Lombok that need the types (`val`, `@Delegate`, `@ExtensionMethod`; delombok runs
without a classpath), the members of the test class itself generated by Lombok (the test class is read from its file,
not through the solver: an `@Slf4j` test class has no `log` among its members).
