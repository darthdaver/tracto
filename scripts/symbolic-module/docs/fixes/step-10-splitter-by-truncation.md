# Step 10 – Rewrite the splitter by truncation

**Date:** 2026-10-26
**Branch:** `22-test-processing-refactoring` (uncommitted, on top of `a022c2ee`)
**Files changed:**
- `src/main/java/star/tracto/preprocessing/utils/TestCaseSplitter.java` (new, 313 lines)
- `src/main/java/star/tracto/preprocessing/utils/TestUtils.java` (old splitter removed: 4,276 → 3,345 lines)
- `src/main/java/star/tracto/utils/javaParser/JavaParserUtils.java` (`isAssertionStatement`, `getLastAssertionInMethodDeclaration`)
- `src/main/java/star/tracto/data/records/OraclesDatasetConfig.java` (key `assertThrows` removed)
- `src/main/java/star/tracto/data/enums/AssertThrowsStrategyType.java`, `BlockStatementsType.java` (deleted, unused)

- docs: `docs/oracles-dataset-config.md`, `docs/design-review-2026-10-26.md`

## Problem

The splitter (`parseSplitTestStatementsBlock`, about 700 lines) built each split test case **forward**: it started from
an empty method, appended the statements one at a time, and emitted a split test case at each split point. Each split
test case was a fresh copy of the previous one, so the splitter did not keep a reference to the block it was filling;
it found it again by searching the copy for the last statement of the expected type
(`getLastStatementTypeOccurrence`). This search, and the per-statement-kind branches around it, caused:

| Defect | Effect |
|--------|--------|
| D1 | A statement after an inner loop was added to the inner loop. |
| D2 (splitter part) | `if (a) { if (b) {..} } else {..}`: the `else` was attached to the nested `if`. |
| D24 | The body of a `synchronized` statement was added after the statement. |
| D26 | A statement containing an anonymous class with methods threw an exception: the test case was dropped. |
| D27 (new) | A labeled loop became a labeled block (`outer: { for (...) { ... continue outer; } }`), which does not compile. |
| D28 (new) | `Runnable r = () -> { ... };` became a bare lambda without its declaration: the split test class did not parse, so **all** the datapoints of the class were lost. |
| — | Try and `switch` statements threw an exception: the test case was dropped (`keep-try-catch` could not work). |

Related defects fixed in the same step:
- **D9**: with the committed configuration (`assertThrows` key missing → `flat`), the splitter crashed on the
  `E e = assertThrows(...)` generated by the normalization, and the test case was dropped;
- **D15**: in `splitTest` an inner `catch (Exception e)` swallowed every error, so the error report of the splitting
  (`error/split/...`) was never written;
- **D23**: for a split test case ending with `assertAll(() -> ..., () -> assertTrue(..))`, the target was the
  assertion inside the last lambda instead of the `assertAll`.

## Decisions applied

- Rewrite by truncation (decision of 2026-10-26, after the comparison of a targeted fix and the rewrite).
- `assertThrows` is a target like any other assertion and the `THROW EXCEPTION` label is removed (decision of
  2026-10-26). The `flat` mode was planned for removal in Step 14; it is removed here, since the new splitter would
  otherwise have to re-implement a mode about to be dropped. Step 14 keeps the rest: the `THROW EXCEPTION` label of the
  `fail(...)` targets, `TokensUtils` and the Python utilities.

## Changes applied

### `TestCaseSplitter`
An AST-in/AST-out class (no file access), extracted according to the incremental restructuring decision:

```java
static List<SplitTestCase> split(MethodDeclaration testCase, OraclesDatasetConfig config)
record SplitTestCase(MethodDeclaration testCase, MethodDeclaration prefix) {}
```

1. **Split points.** Collected in source order within the blocks of `if` (and `else if` chains), loops,
   `synchronized`, labeled statements, `switch` entries, try/catch/finally blocks, and the block of a lambda expression
   passed to (or assigned by) a statement that is not an assertion, when it is the only one at the level of the
   statement. Any other statement is one unit: an assertion, a statement declaring an anonymous class, an
   expression-bodied lambda. With `split = assertion` the split points are the assertions
   (`JavaParserUtils.isAssertionStatement`); with `split = statement` they are the units, and the compound statements
   without split points within them (for example an empty loop), as before.
2. **Truncation.** For each split point, the test case is copied and, from the split point up to the body, at every
   level the code that follows is removed: the following statements of a block or of a `switch` entry, the following
   entries of a `switch`, the `else` branch when the split point is in the `then` branch, the content of the following
   catch blocks and of the finally block (their headers are kept, since a try statement needs them). The orphan
   comments (comments not attached to a statement) of these blocks are removed too if they follow the split point in
   the source. The split test prefix is the same copy without the split point.
3. **Block bodies.** The body of an `if`, loop or non-loop labeled statement that is a single statement is wrapped in a
   block first, as the old splitter did, so that the split point can be removed from it. The body of a labeled loop
   is not wrapped (D27).
4. **Checks.** `num-assertions-match` compares the number of assertions of the test case with the number of split
   points (before: the comparison was made for each block, with the same result in practice).
   `keep-statements-after-last-assertion` adds the whole test case as last split test case if it differs from the last
   one.

### `TestUtils.splitTest`
Calls `TestCaseSplitter.split`. A test case that cannot be split is logged and saved in `error/split/...` (D15) with
`saveTestCaseReport` (the former `collectNormalizationErrors`, now used for the three reports: normalization errors,
discarded test cases, splitting errors). Removed: `parseSplitTestStatementsBlock`, `addStatement`, `addCatchClause`,
both `initializeSplitTestCase`, the `flat` handling of `assertThrows` (the call written in the prefix, the fake
`fail("THROW EXCEPTION")`, the `throws` clause added to the split test cases) and the unused locals.

### `JavaParserUtils`
- New `isAssertionStatement(Statement)`: an `assert` statement, or an expression statement whose expression (or the
  initializer of the variable it declares) is a call to a JUnit assertion. Used by the splitter and by
  `getLastAssertionInMethodDeclaration`, so that both phases share the definition.
- `getLastAssertionInMethodDeclaration` walks up from the last statement of the method and returns the **outermost**
  assertion statement (D23); an assertion that is the body of an expression lambda passed to another call
  (`values.forEach(v -> assertTrue(v > 0))`) is not a split point and is not returned.

### Configuration
The key `assertThrows` was removed from `OraclesDatasetConfig`, with the enum `AssertThrowsStrategyType`. A configuration
that still contains it is rejected when it is loaded (`Unrecognized field "assertThrows"`). `BlockStatementsType`,
used only by the old splitter, was deleted.

the new tests for `switch`, labeled loops, lambdas assigned to variables, try statements, `assertThrows` targets).
Three new characterization tests passed on the old splitter and pin its behaviour for the rewrite: the prefix within a
loop, the wrapping of single-statement bodies, statement split within a loop.

## Verification on real projects

Fresh copies of the two repositories, committed configuration of each version, compared with Step 9 datapoint by
datapoint (key: test class and split test case):

| Project | Step 9 | Step 10 |
|---------|--------|---------|
| crawler-commons | 13 classes, 634 datapoints | 13 classes, **649** datapoints |
| java-uuid-generator | 8 classes, 349 datapoints | 8 classes, **369** datapoints |

No datapoint was lost, and the splitter no longer drops any test case (10 before). Every difference falls into one of
these categories:

| Change | crawler-commons | java-uuid-generator |
|--------|-----------------|---------------------|
| Datapoints of test cases recovered from D9 (generated `assertThrows` declaration) | +13 (2 test cases) | +13 (5 test cases) |
| Datapoints of test cases recovered from D26 (anonymous class) | +2 (1 test case) | +7 (2 test cases) |
| Target `THROW EXCEPTION` → the `assertThrows` statement (plain `assertThrows` in the test case) | 5 | 0 |
| Prefix changed by comments only: orphan comments that precede the split point, now kept (the old splitter dropped all orphan comments) | 57 | 32 |
| Prefix changed in its code | 0 | 0 |

No prefix changed in its code, so D1, D2, D24, D27 and D28 do not occur in these two projects; they are covered by
the tests.

The first A/B run showed 4 more comment changes in crawler-commons: orphan comments located **after** the split point
(for example `// with merged groups`, describing the following assertions) leaked into the prefixes, because the
truncation copied the orphan comments of the blocks. The truncation now removes them by source position, and a test
covers it. A manual check of `SiteMapCrossSubmitValidatorTest.testValidateCrossSubmitSites` confirmed the positions of
the comments that remain: the block comment before the first assertion appears from `split_0`, the one before the
eighth assertion from `split_7`.

## Known remaining issues

1. The normalizer still attaches an `else` to a nested `if` (D2, normalization part): Step 11.
2. A `fail(...)` target is still the label `THROW EXCEPTION`: Step 14.
3. Orphan comments before the split point are now part of the prefixes. They are part of the test as written, but
   comments in general deserve a decision (see also the misplaced comments in declarations noted in Step 9).
